# Auriga Development Guidelines

This document is the authoritative guide for human developers and coding agents working on the Auriga repository. Before making changes, trace the full end-to-end call path, then complete the implementation, regression tests, and documentation updates while preserving existing user work. Explicit user authorization remains in effect across turns; routine reversible fixes do not require repeated confirmation.

If `lab/AGENTS.md` exists at the repository root (a separately cloned private companion repository), read and follow it alongside this file.

## Required Reading Before You Start

1. [README](README.md): Product goals, publicly exposed tools, and standard workflows.
2. [Implementation Architecture](docs/development/architecture.md): Module responsibilities, state ownership, and call paths.
3. [Tool Contracts & Plugins](docs/development/tool-plugins.md) and [Extension Guide](docs/development/extensions.md): How to add or modify tools, skills, and robot backends.
4. Depending on the scope of your change, read the [Shared Protocol](docs/design/shared-protocol.md), [Unified Actions](docs/development/unified-actions.md), [Actor Information Boundary](docs/development/actor-information-boundary.md), and [Validation Guide](docs/development/validation.md). Historical design documents describe broader architectural targets; the current truth is defined by the tool registry, schemas, and contract tests.
5. Before launching, resuming, or organizing benchmark experiments, read the [Experiment Library](docs/development/experiment-library.md), the [Experiment Completion Hook](docs/development/experiment-completion-hook.md), and the "Experiments & Evaluation" section below to verify existing configurations, baselines, and execution batches.

When checking Codex capabilities, prefer official OpenAI documentation; if the official site is unreachable or lacks a specific detail, consult the [Codex Docs mirror](https://www.codex-docs.com/docs). Any conclusions regarding APIs, hooks, task planning, or version support must be verified against the pinned SDK/CLI version in this repository, generated schemas, or live invocations—always distinguishing general documentation from locally verified behavior.

**The default project interpreter is the `Auriga` environment managed by Miniforge.** Always use `mamba run -n Auriga python` (or `python` after explicitly activating the `Auriga` environment) for development, tests, the gateway, the evaluation queue, and offline scripts. Never create or recreate a `.venv`, and do not fall back to system Python or an unpinned `codex` binary on `PATH`. The actual SDK/CLI version and binary path must be verified against the `Auriga` environment and recorded with runs. Temporary installation directories created during wheel checks are strictly for verifying out-of-tree installation, not for running the project; RoboDojo and OpenPI continue to run in their own configured isolated interpreters.

## Inviolable Architectural Boundaries

**Context carries only necessary information.** Never place non-essential data—especially build, provenance, or storage metadata—into the Codex context window. For every model-visible field, you must be able to explain how it helps the model make its current judgment or construct its next tool call; if it serves no operational purpose, remove it from both the producer and the presentation layer. Hash digests must never enter model-readable context, nor be replaced with verbose placeholder disclaimers. Object identifiers required for targeting must use reversible short references (`short_id`). Control-critical state—such as plan revisions, execution status, error diagnostics, measurement precision, and evidence uncertainty—must be preserved.

Preserve native Codex instructions, tool catalogues, and general coding capabilities; do not overwrite its default foundation or strip native capabilities merely to shorten prompts. Encourage the model to write helper code and build analysis tools within its sandbox and permitted observations; context reduction targets redundant instructions and non-essential metadata added by the Harness.

- **One Physical Entry Point.** Every action that affects the observed world must pass through `Harness.execute`. New plugins must use `ToolContext.execute` and never invoke robot workers directly, fabricate action receipts, or advance the simulator. Both the interactive actor and helper programs share the same `ToolSpec`; the `trusted_legacy` role exists solely for existing trusted Python integrations.
- **Strict Separation of Facts and Presentation.** Programs and tests must consume `ToolResponse.kind` and `ToolResponse.data`—never parsing human-readable display text, `stdout`, or HTTP status codes to infer whether a physical action succeeded. If image rendering or presentation fails after a physical action has executed, the typed receipt must be preserved along with the delivery error; the action must never be silently re-sent. When a reliable receipt, stop confirmation, or step count is missing, keep the field as `unknown` or `null`.
- **Complete Tool Contracts.** Every tool must declare its input/output schema, role, effect, availability, and API version, and must be validated across both the actor and program entry points. Parameter meanings, physical units, defaults, bounds, and applicability belong in the tool definition itself. **Whenever you add a tool, stage parameter, or helper function, you must document the physical meaning, unit of measurement (e.g., `m`, `rad`, `deg`, `s`), default behavior, and applicable scenario for every field in the contract description—bare parameter names without explanations are strictly forbidden. Any inline helper library (such as `scene3d_helpers`) must provide clear function signatures, parameter/return descriptions, and call examples so the model never has to guess.** Generate model-facing documentation and runtime validation from the same single contract rather than patching parameter docs into task prompts, and verify the actual payload delivered after native tool conversion. Reuse the central registry and `ToolContext`; do not add parallel allowlists, name-based routing tables, or implicit module scanning.
- **Restricted Information Sources.** The actor and any auxiliary models may read only permitted formal observations. Hidden simulator state, evaluator internals, raw observer artifacts, credentials, and developer diagnostics must never enter model context. The main model, auxiliary models, program responses, and text artifacts share the same metadata scrubber and short-ID mapping; resumed session histories are scrubbed again at the actual Responses API egress. Raw typed data and observer archives retain full verification facts, but the raw archive must never be exposed as a backchannel to the model.
- **State Modified Only by Its Owner.** Idempotent replays return historical receipts without rolling back the active plan. Any action that could advance physical state but lacks a terminal observation invalidates prior observations; taking a fresh observation does not clear an `unknown` or `stop` gate. Scene entities validate clock alignment and freshness against the exact set of observations they reference.
- **Traceable Archives and Scoring.** Sealed run archives must be opened via `open_read_store` (reading a private copy when a WAL file is present, or opening immutable read-only when no WAL exists); active runs use the live WAL reader. Imported runs preserve their native summary while recording import lifecycle metadata separately. Original images, reconstructed images, task scores, and integrity checks are reported independently; unknown cases remain in the fixed protocol denominator.

## Implementation & Collaboration

Search for all callers, tests, configurations, and exports before editing. Fix shared root causes and reuse existing helpers; do not introduce speculative frameworks, dependencies, feature flags, or duplicate contracts for hypothetical future requirements. Non-trivial logic must include regression tests capable of reproducing the original bug—especially covering exceptions, partial execution, retries, permissions, and backward compatibility with older archives.

Independent tasks with non-overlapping file ownership may be delegated in parallel; the integrator is responsible for cross-review, final verification, and delivery. Never overwrite uncommitted changes in other worktrees, rewrite unrelated Git history, or disturb running experiments or shared services. Remote execution, synchronization, deployment, and archive migration must only happen within the explicit scope of a user request and must never be triggered implicitly by local tests.

### Experiments & Evaluation

The Experiment Library reads an optional registry at `<archive_root>/service/experiment-groups.json` that describes each experiment group's name, purpose, iteration lineage, and baseline (see [Experiment Library](docs/development/experiment-library.md#registry-file-format)). The registry maintains definitions and relationships only; scores, run states, and recordings always come from the raw run archives.

- **Establish the Comparison Protocol First.** Select the baseline and document the rationale before launching a comparative experiment. Controlled comparisons must align task, variant, seed, layout, budgets, and all conditions outside the experimental intervention; if source revision, model, provider, SDK, prompt, or memory change simultaneously, document each difference explicitly. When a reliable baseline is absent, treat the run as exploratory and do not claim single-factor gains. Verify the configured model and the actual served model independently.
- **Fixed Protocol and Denominator.** Specify the exact case identities for every condition in the manifest using integer `seed` and `layout` values. Prepared, unstarted, cancelled, invalid, and unscored cases stay in the fixed denominator. Recovery runs must be a strict subset of the original protocol; when merging, preserve the first formal score in execution order for each scene (including `0` and formal task failures), using a recovery result only when no prior formal score exists—never cherry-picking the best score.
- **Separate Logical Identity from Execution Attempts.** Group `baseline` and `candidate` conditions separately; never mix them. Every new execution or retry must use a fresh run directory rather than reusing paths from earlier batches; never move or rename raw run directories or recordings for cosmetic organization.
- **Record True Provenance and Timestamps.** Record the exact source revision executed; if uncommitted changes exist, save a verifiable patch or snapshot reference rather than backfilling `HEAD` from the current worktree after the fact. Actual start and end timestamps must come from identity-matched runtime events and native summaries stored in UTC; registration, import, and preparation times must never impersonate execution start times, leaving missing evidence as `null`. None of this audit metadata may be injected into the experimental actor's context.

### Long Experiments, Queue Scheduling & Completion Hooks

Any benchmark that waits on a model, native worker, or GPU must be launched through `auriga.apps.evaluation.queue` (`scripts/benchmark_queue.py` is a compatibility wrapper). Multiple independent cases must be placed in a single manifest and scheduled in parallel by the queue using the requested `max_parallel`; each case must use its own run directory and isolated memory, while cases sharing the same source revision share a single frozen checkout. Never split cases into ad-hoc background processes, launch them serially by hand, start gateways directly in parallel within an agent turn, or cobble together custom shell monitors. The manifest, source binding, concurrency limit, and completion hook must all be fixed and recorded before submitting the queue.

Once the queue has started with `--wake-thread`, `--wake-codex`, and `--wake-enabled`, end the current agent turn immediately and wait for the queue's completion notification. While waiting, do not manually poll `state.json`, tail logs, query PIDs/GPUs, loop with `sleep`, refresh web pages, or spawn watcher subagents—none of these may substitute for the completion callback. Never declare an experiment successful merely because the queue is `running`, `finished`, or the hook receipt says `sent`, and do not automatically cancel, restart, or append experiments. Unless the user asks to stop, never cancel a running queue just because the current turn is ending; let the scheduler run and wake the next turn via the hook.

Only after receiving the completion callback should you read the final queue state, each case's `summary.json`/`evaluation.json`, request identity, native cleanup status, and failure evidence. `queue=finished` only proves that the scheduler finished; success rates and scores must come from the official evaluator. If the callback has not arrived or is incomplete, report the status as unknown and stop without fabricating results. See [Experiment Completion Hook](docs/development/experiment-completion-hook.md) for the exact hook protocol.

## Delivery & Release

Run all affected checks according to the [Validation Guide](docs/development/validation.md); when modifying public boundaries or cutting a release, run the full CPU, Web, and wheel packaging suites. Record the exact revision, commands, results, skips, and environment constraints. Passing CPU, package, or browser tests only proves the corresponding software layer; claims about native motion semantics or task performance require independent native evidence under frozen conditions.

Inspect `git diff` and check for sensitive data before committing. Configuration examples must never contain real keys, and Git must never track run directories, model weights, large videos, or machine credentials. Documentation links must point to real code and tests; when changing a public contract, update the corresponding guide as well as the README and [Documentation Index](docs/README.md). When cutting a release, verify the package version, annotated tag, branch ancestry, and working tree status, preserve historical tags, and push normally without rewriting existing tags.

## First Principles of Embodied Control & Anti-Pitfall Philosophy

This section distills recurring design mistakes and hard-won lessons from embodied manipulation development. Review it before changing any Harness behavior.

### Supreme Design Principle: Eliminate Hardcoded Heuristics and Black Boxes; Return Full Autonomy to the Model

**Every drop in generalization, cross-iteration regression, and performance oscillation we have experienced traces back to the same root mistake: hardcoding task logic, rules, and magic numbers inside the Harness as a black box invisible to the model.**

When a developer sees a specific manipulation task fail, the most tempting—and most destructive—mistake is to bury new heuristic rules, magic thresholds, or hidden state machines inside low-level modules (such as `batch_motion.py`, `action_state_ledger.py`, or `vggt_height_service.py`). Doing so inevitably causes three failure modes:
1. **Stripping Model Autonomy**: When logic and thresholds are hardcoded in the background or hidden from tool schemas, the model cannot **autonomously select, judge, configure, or invoke** behavior appropriate for the visual and physical scene in front of it.
2. **Cognitive Misalignment from Hidden Black Boxes**: When the Harness secretly guesses stage intent (e.g., covertly distinguishing pre-grasp from pre-release, maintaining a hidden cross-stage `compliant_support_z` cache, or silently mutating tolerances and gripper guards), the model has no idea those hidden rules exist—nor why one stage succeeds with a 6 cm error while another fails at 6 mm, or why holding a thin cloth causes every subsequent move to pause mysteriously.
3. **Cross-Task Overfitting and the Seesaw Effect**: Embodied manipulation spans rigid peg-in-hole insertion, deformable cloth folding, compliant nesting dolls, and in-place nut fastening—each governed by drastically different physical constraints. Any hardcoded scalar threshold or heuristic rule tailored to Task A will inevitably break Task B, trapping overall benchmark performance in endless oscillation.

**Before writing or modifying any code, enforce the "Four Self-Check Red Lines":**
- **Question 1 (Is it hardcoded?)**: Am I hardcoding a magic number (such as `0.075`, `0.0055`, `+0.002`, `-0.02`), a shape/step threshold, or a task-specific `if-else` patch for a task that just failed? **If yes, stop immediately!**
- **Question 2 (Is it a black box?)**: Is this logic, state transition, or effective tolerance/guard invisible to the model? **If yes, dismantle the black box and replace it with a stateless, transparent mechanism!**
- **Question 3 (Does the model have full agency?)**: Can the model express its physical intent through public, orthogonal tool parameters (such as stage-level `position_tolerance_m`, `orientation_tolerance_rad`, `max_upward_dz_m`, `stall_guard_preset`, `grip_guard_preset` / `min_aperture_m`)? If the model lacks a control knob, **expose the parameter in the tool contract with clear physical semantics and defaults—never delete parameters and let the backend guess on the model's behalf!**
- **Question 4 (Are receipts honest and transparent?)**: Are parameters explicitly set by the model respected 100% without silent background overrides? Do `preview` and `execute` receipts transparently report the `effective_tolerances` and true measured physical residuals?

### The Four Core Laws (Harness First Principles)

1. **No Implicit Assumptions or Silent Background Overrides.**
   - Never silently alter parameters or geometric assumptions explicitly passed by the model, and never remove public parameters from tool schemas to replace them with background heuristics (**Anti-pattern 1**: forcing `vggt_height_mode="default"` and silently overwriting the model's explicit `plane_origin_m=[0,0,0.765]`, which directly shifted rays and broke `sweep_blocks` and `plug_in_charger`; **Anti-pattern 2**: removing `max_upward_dz_m` from the tool schema and replacing it with hidden `_is_open_jaw_pre_grasp`, `_is_closed_jaw_pre_release`, `compliant_support_z` state machines and `0.075 m / 0.0055 m` magic numbers in `batch_motion.py`, depriving the model of stage-level compliance control).
   - Never use noisy monocular bounding boxes or action counters as a "blind referee" to scold or block the model before or after execution (**Anti-pattern**: firing false-positive aspect-ratio warnings in `grasp_preview_3d` from oblique 2D projections, or hardcoding three-tier nag messages and a two-step zero-displacement `no_scene_progress_warning` in `action_state_ledger.py` that misdiagnosed normal in-place nut turning in `fasten_screws` as a deadlock and pressured the model into abandoning its target).
2. **Never Overfit to Any Single Task.**
   - Every mechanism must be grounded in universal rigid/deformable contact physics, robot kinematics (such as principal-branch $[-\pi, \pi]$ joint equivalence classes, parallel-jaw symmetry, and true zero-aperture calibration), and transparent parameter contracts.
   - Never hardcode task-specific workflows, heuristic shape thresholds, dedicated rule branches, or global threshold tweaks to rescue an individual task (**Anti-pattern**: artificially lowering the global `OT` filter threshold in `vggt_height_service` to detect a thin object, or making `active_arm_grip_guard` persistent across all subsequent move stages with a hardcoded `ap_after <= 0.0005`, which caused every move while holding thin cloth in `fold_clothes` to abort as an empty grasp). Every change must demonstrate Pareto improvement across a task suite containing both positive and negative cases.
3. **Return Decision-Making and Control Authority to the Model (Select, Judge, Configure, Invoke).**
   - Perception and execution modules exist to report objective geometric measurements/estimates, pre/post-action 3D state diffs (`object_state_delta`), physical contact attribution (`contact_object_3d`), true measured residuals, and `effective_tolerances`. They must never name objects for the model, dictate grasp targets, inject rigid formulas, or decide the next strategy (**Anti-pattern**: hardcoding `grasp_yaw + (target_yaw - yaw_deg)` in prompts, which caused the model to plug noisy oblique monocular `yaw_deg` estimates into the formula and twist upright pegs off-axis).
   - Tool contracts and parameter descriptions provide orthogonal, transparent control knobs and clear coordinate/physical conventions so the model can choose presets or set numeric bounds based on visual evidence, preserving adaptability under occlusion, clutter, and unexpected contact.
4. **Build Ergonomic, Low-Friction Tools That Empower the Model.**
   - **Zero-Turn-Tax Sideband Information + On-Demand Deep-Dive Helpers**: Deliver high-value, low-noise 3D geometric references alongside observations at zero extra turn cost (such as the inline `object_table`, principal-branch `across_yaw_deg`, `stand_upright_angles_deg`, true `pad_z_m` for thin table-flush and stacked objects, and `scene3d` point-cloud handles); pair them with forgiving, flexible `scene3d_helpers` (supporting flexible argument order, stereo ray triangulation `triangulate_rays`, in-hand principal axis estimation `in_hand_axis`, and unclipped local height extrema `surface_extrema`) and explicit on-demand `obstacle_object_ids`. This minimizes tool-call friction without forcing the model to pay an extra turn tax for separate planning tools.
   - **Explainability Red Line for Tools and Helpers**: Every new tool, parameter, or helper function must document its **physical meaning, unit (`m`, `rad`, `deg`, `s`), default behavior, typical range, and usage example** directly in its `ToolSpec` schema or model-visible documentation—never ship undocumented parameters or opaque helper functions.

### Motion Control & Closed-Loop Guard Guidelines

5. **Enforce True Stage Terminal Accuracy & Parameter Transparency: Respect Explicit Model Tolerances, Report Honest Physical Residuals, and Never Mask Failures as `"completed"`.**
   - In a multi-stage batch (`[approach -> grasp -> lift -> align -> insert -> release]`), terminal accuracy verification at intermediate stages is the physical firewall that prevents error amplification across the batch.
   - Expose tolerance and vertical compliance controls (`tolerance_preset`, `position_tolerance_m`, `orientation_tolerance_rad`, `max_upward_dz_m`, `stall_guard_preset`) per stage, and return `effective_tolerances` transparently in both `preview` and `execute` receipts. When the model explicitly specifies `max_upward_dz_m` or `position_tolerance_m`, enforce the exact requested bound—never maintain hidden cross-stage state machines or silently widen `3 mm / 5 mm` tolerances to `5.5 mm` or `75 mm`, which falsely marks deflected intermediate stages as `completed` and lets subsequent open-loop stages compound the error.
6. **Align Physical Guards with True Hardware Zero Points and Keep Them Fully Configurable.**
   - **Distinguish Uncompliant Pre-Grasp Descent Stalls from Explicit Compliant/Contact Placement**: During an open-jaw descent where wide vertical compliance was not requested, if fingertips collide with the top of an object and stall above the target, honestly intercept the stage with `tracking_error` and surface the top-level `contact_block_summary` (`blocked_above_target` and `approach_shortfall_m`) rather than closing the gripper in mid-air and discarding the top-contact diagnosis. When the model intends to press against a support surface or perform compliant insertion, it explicitly sets `stall_guard_preset="contact_stop"`, `tolerance_preset="compliant"`, or stage-level `max_upward_dz_m`.
   - **Transparent, Object-Adaptive `grip_guard` Thresholds**: A true empty close on the hardware reaches `0.0000 m` aperture, thin walls/rims/stems typically settle around `2–13 mm`, and ultra-thin deformable fabrics (such as clothing) compress to nearly `0.0000 m`. The model controls the guard via `grip_guard_preset` (`none`, `thin_object`, `non_empty`, `rigid_object`, `wide_object`) or explicit `min_aperture_m` / `max_aperture_m`. Post-grasp lift slip detection fires at most once—on the first upward move immediately following gripper closure when a sharp slip occurs (`jaw_delta <= -0.08` and `ap_after <= 0.002 m`)—and must never remain armed across later transport stages to block thin-object manipulation.
7. **Guard Against the "Checkpoint Tax" and Multi-Mechanism Coupling.**
   - **Exception-Driven Pauses Over Unconditional Per-Stage Pauses**: In long-horizon tasks manipulating many objects, pressuring the model into inserting explicit `observe` / `checkpoint_after_gripper` pauses on every stage doubles total batch interruptions and rapidly exhausts turn and native step budgets (`stopped` inflation). Let normal grasps run smoothly end-to-end while relying on hardware-level `grip_guard` and `stall_guard` to pause automatically only when an anomaly (empty grasp, slip, or stall) actually occurs.
   - **Controlled Single-Variable Ablation & Principal-Branch Anti-Windup**: When combining multiple changes yields `1 + 1 < 2`, isolate variables via code-level diffs and stage telemetry (`tracking_error`, `grip_guard`, `vertical_compliant`, $|q_0| > \pi$). Equivalent revolute joint replanning must prioritize the principal branch $[-\pi, \pi]$ so joints never ratchet past $\pm\pi$ into the $\pm 2\pi$ software limits.
   - **LPT (Longest Processing Time First) Parallel Scheduling**: Sort large benchmark manifests in descending order of historical weighted wall-clock duration and pair them with high-concurrency queues and multi-key load balancing so long-tail tasks never bottleneck overall batch turnaround time.
