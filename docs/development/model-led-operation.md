# Model-Led Operation: Transport, Risk Advisories, and Sol Verification

This document describes the model request transport policy, the division of responsibility between deterministic code and model judgment, and optional Sol operation verification. Model responses have no arbitrary local cutoff deadline, and explicit transient service errors are automatically retried by the Harness. Code provides geometric and kinematic computations while leaving primary object and contact judgments to the model. When enabled, Sol verifies manipulation operations through the official Codex agent interface, receiving only the necessary evidence without inheriting the primary model's conversation context. Frozen source trees and results from historical experiments are never rewritten.

## Model Request Transport

Earlier versions enforced a local 90-second total response timeout on `communicate` in the standalone HTTP worker, waiting until the entire HTTP stream closed before inspecting the response and retrying up to 12 times on timeout. During RoboDojo evaluations, requests that had already received HTTP 200 and initial response bytes were repeatedly aborted by this local deadline; because partial streams were not preserved, it was impossible to tell whether the upstream server was actively generating tokens or waiting to close the connection.

Both `ModelRequestProxy` and the standalone `ResponsesClient` now follow a deadline-free streaming design:

- **No local request deadline or socket read timeout.** Active requests are never aborted or resent merely for taking a long time. Only explicit, retryable service errors trigger automatic Harness retries (up to 12 retries by default, for a total of 13 HTTP attempts).
- **Completion upon terminal SSE event.** A request finishes as soon as the complete terminal SSE event arrives, without waiting for HTTP connection EOF. Only complete, valid, successful responses can deliver tool outputs and count toward the 180-request episode budget; failed or incomplete responses never execute tool calls.
- **Targeted backoff retries.** HTTP `408`, `429`, `5xx`, and explicit transient overload or rate-limit errors trigger exponential backoff with jitter (honoring positive `Retry-After` headers when present). Unrecoverable errors—such as authentication failures, invalid request payloads, context-length or quota exhaustion, and safety refusals—fail immediately. Unknown disconnects, missing terminal events, `incomplete` streams, and user cancellations are not retried as standard service errors, and tool outputs from failed attempts are never delivered.
- **Explicit cancellation and zero SDK retries.** User cancellation, stop signals, and process exits still interrupt in-flight requests immediately. Built-in SDK request and stream retries are set to `0` so that the Harness alone owns retry logic without nested retry amplification. Because the SDK lacks an infinite-idle sentinel, it is configured with the maximum signed 32-bit integer millisecond timeout plus local keepalives, imposing no practical response cutoff.
- **Long-cooldown transport recovery.** If normal retries are exhausted or an upstream stream breaks mid-transfer (`transport_incomplete`, such as `IncompleteRead`), the proxy enters the `model.transport_recovery` cooldown schedule (defaulting to at most 10 rounds: 60, 120, 240, and 480 seconds followed by 600 seconds per subsequent round, capped at 3,600 seconds of total cooldown per episode, with each single cooldown staying below the 1,800-second inactivity timeout) before resending the exact same request body. Codex observes only keepalive heartbeats on the original request—no extra turns, prompts, or tool calls are injected, leaving the model context untouched. Because the RoboDojo simulator pauses during model inference, waiting does not advance the physical world; before and after each cooldown window, the Workbench verifies that no action is currently executing or in an `unknown` state, no program is active, action admission remains open, and the native episode has not terminated, aborting recovery otherwise. Recovery activity is logged to private observer events (`model.model_transport_recovery_scheduled`, `model_transport_recovered`, and `model_transport_recovery_denied` with reason) and summarized under `runtime/model_requests.transport_recovery` (rounds, recovered calls, and total cooldown seconds) without entering model-visible context. Setting `max_rounds=0` restores the baseline retry behavior.
- **Infrastructure failure handling and activity supervision.** If an unretryable error occurs, recovery is denied, or recovery rounds are exhausted, the Harness reports an infrastructure failure and concludes the run without triggering actor continuation. When a retryable outage recovers, the original logical request resumes seamlessly without manual intervention. Runtime liveness supervision tracks a 30-minute (1,800-second) global inactivity window across all sources: a hung request or backoff sleep does not reset the timer, whereas actual upstream network byte progress refreshes the activity clock without imposing a cap on single-response or full-episode wall-clock duration.
- **Program budget exclusion for Sol calls.** When a program invokes Sol review, the wall-clock time spent waiting for that model request is excluded from the program's execution timeout, restoring the remaining program budget once the model responds (waiting on other programs or the primary actor does not credit a program's budget). Per-action robot timeouts, local program compute limits, and explicit cancellations remain enforced. The legacy 90-second per-step model-wait buffer in skills has been removed.

Runtime supervision for benchmarks and `--exit-after-turn` aggregates monotonic activity clocks across the model proxy, Codex code execution, robot/simulator workers, and running programs. The model proxy records streaming progress in real time as upstream bytes arrive rather than waiting for the full request to finish (synthetic local keepalives do not refresh the activity clock). If all sources remain completely inactive for 1,800 consecutive seconds, the Harness cancels in-flight requests and terminates the run with `runtime_inactivity_timeout`, preserving an unscored infrastructure-failure record; as long as any component makes progress, the episode continues. `model_wait_seconds` continues to exclude model inference time from program budgets without exempting the run from global inactivity supervision. Environment initialization, single-action execution, and local program compute timeouts remain independently enforced.

An unexpected downstream disconnect from Codex is treated as an unknown response outcome that locks subsequent requests against automatic reconnection retries. Explicit cancellation also aborts requests that have not finished reading their request body and releases their reserved call budget.

## Division of Responsibility Between Code and Model

Deterministic code enforces hard execution contracts: environment and observation identity, finite numeric values and valid quaternions, action payload consistency, single-action-writer exclusivity, stop-state gates, whether the native planner returned a valid trajectory, and verification that a cached plan is unconsumed and its measured start state is still current. Fixed robot geometry, the nominal 88.8 mm maximum jaw aperture, coordinate frame transforms, and FK/IK solvers serve as deterministic calculation tools, which are distinct from estimating the shape, center of mass, or surface friction of unknown scene objects.

Object bounding volumes and held-object extents come from model estimates derived from RGB views and camera calibration. Collision review approximates robot links as spheres and fingers/objects as oriented boxes or bounding volumes, sweeping them along the planned joint trajectory to compute clearances and intersections. Fixed sampling intervals, conservative curvature bounds, safety margins, and contact rules can flag geometric risks, but they do not constitute proof of physical collision or task infeasibility.

Consequently, review outputs report `assessment_role="advisory"` and `decision_owner="model"` with a status of `risks_detected`, `conditional`, or `unavailable`, and no longer emit a gating `execution_allowed` boolean. The primary model decides whether to execute a cached plan, adjust the trajectory, refine its geometric estimates, or capture a new observation. Direct pose and multi-waypoint execution modes remain available without requiring a prior preview, and closing the gripper is never blocked by the absence of a prior grasp plan. A previous native planning failure on the same nominal target is recorded as historical evidence rather than used to automatically block a well-founded retry.

Diagnostic contact parameters remain available to clarify expected interactions:

| Parameter | Retained Geometric Approximation | Current Advisory Meaning |
|---|---|---|
| `contact_entity_id` | Target finger-contact window within `60 mm` and `20°` of the terminal pose | Annotates declared target contact while preserving raw overlap records; does not grant execution permission |
| `initial_contact` | Monotonic separation of initial overlaps, conservative curvature bounds, and terminal clearance check | A failed check means the current geometry and sampling resolution did not prove clean separation, not that withdrawal is physically impossible |
| `placement_contact` | Nominal geometry of the held object against the top of the support surface (`2 mm` default tolerance, `3 mm` ceiling) | Indicates whether the approximation supports a placement interpretation without restricting the contact motion chosen by the model |

`contact_overlaps` retains all intersecting objects, robot parts, timestamps, and estimated penetration depths explained by the categories above rather than hiding risks behind summary labels. If collision review or overlay rendering fails after the native planner has already generated a trajectory, the cached plan is preserved and its `plan_id` is returned alongside an `unavailable` assessment note; only a native motion-planning failure leaves no executable trajectory. The legacy eight-consecutive-read-only-call gate has been removed, while task-level planning requirements remain governed by `task_plan`.

## "Unable to Proceed" Declarations and Recovery Guidance

In recorded RoboDojo episodes, before declaring that a task could not be continued, the model had often already attempted pose adjustments, vertical and lateral withdrawals, finer object proxies, intermediate staging, switching arms, or pushing objects. Several abandoned lift or retreat trajectories would have succeeded with finer waypoint sampling, and some episodes succeeded even after an earlier "unable to proceed" declaration. Such declarations therefore indicate at most that the current attempt was blocked—not that the task is physically infeasible, nor conversely that a safe recovery route is guaranteed to exist.

While earlier prompts already suggested short test lifts, adjusting grasp poses after an empty lift, inspecting feedback after partial execution, and varying position or orientation—and the legacy completion hook mainly urged continuation or returning home—current recovery guidance combines measured-pose home verification with structured recovery instructions: identify the specific physical obstruction and prior attempts, distinguish local search failure from global impossibility, evaluate alternative grasp points, approach angles, arms, staging surfaces, or viewpoints based on evidence, avoid repeating identical rejected declarations without new information, and explicitly state what evidence is still missing if no viable action can be found. Fixed coordinates or hardcoded action recipes are never injected in place of model-authored actions.

When repeated collision risks arise, guidance suggests multi-segment approaches or retreats that vary intermediate positions and orientations to route around obstacles. In the current unified action interface, `robot_action` accepts up to 32 stages per batch (up to 16 per arm), replacing the legacy `robot_move_grasp.via_grasp_poses` and `robot_execute_ee.action.path.waypoints` tools removed in the 2026-10 refactor. When a multi-stage path is clear, waypoints can be submitted in a single batch; when intermediate visual or proprioceptive feedback could alter subsequent choices, the motion should be split into shorter actions with observations in between. A single multi-waypoint action executes open-loop across its intermediate waypoints without model intervention, and subdividing an obstructed straight line into collinear segments does not create obstacle clearance.

## Sol Operation Verification

By default, `features.visual_review_model` is `null`, which disables `vision_review` (including `evidence_mode="operation"`, which replaced the standalone `operation_verify` tool in the 2026-10 refactor). Setting `features.visual_review_model="gpt-6.1-sol"` re-enables the tool. When enabled, verification runs in an isolated Sol subagent using `gpt-6.1-sol` at `high` reasoning effort, sharing the episode's 180-request total budget across the primary actor, helper agents, and context compactions.

Pre-action planning is reinforced through the `task_plan` guidance: before moving, identify potential interference from neighboring objects along the full arm, fingers, held object, and withdrawal path; for unfamiliar or irregularly shaped objects, compare candidate grasp regions, closing directions, grasp stability, and downstream placement feasibility; for tight destinations or containers, verify final object position, orientation, support, release clearance, and retreat space. The model selects multi-segment poses according to the scene and splits actions wherever intermediate feedback is needed. Trajectory preview remains an optional aid, with no object-category rules, fixed manipulation sequences, or mandatory execution gates.

Invoking `vision_review` triggers `CodexEvidenceAgent`, which launches an isolated official Codex `app-server` process via the Python SDK for each call, starts a clean session with `thread/start(ephemeral=true)`, and submits the selected evidence via `turn/start(input, outputSchema)` to obtain structured JSON output. Every invocation is completely stateless—it never forks or resumes the primary actor thread, never receives the primary conversation history, runs in an empty dedicated working directory with specialized instructions, and registers no dynamic robot tools. Global configuration for the helper process disables project documentation discovery and native memory (because CLI thread-level feature overrides alone do not reliably isolate those background features in a shared process). While the official runtime may still attach its built-in native tool declarations, the helper prompt restricts evaluation strictly to the supplied evidence, and any response containing tool activity is rejected. Canceling a verification call interrupts only the helper process, while authentication and the shared 180-request budget remain managed by the Harness proxy. The legacy custom HTTP/SSE client for Sol has been removed; offline visual probes also use this official agent interface.

This design follows the [Official Codex App Server Documentation](https://developers.openai.com/codex/app-server#start-or-resume-a-thread) (which distinguishes starting a fresh ephemeral thread from forking thread history and supports per-turn `outputSchema` enforcement) and the [Official Subagents Documentation](https://learn.chatgpt.com/docs/agent-configuration/subagents) (which defines subagent context isolation). Starting a fresh official agent thread guarantees minimal context and is triggered deterministically by the verification tool without requiring the primary model to manage subagent spawning.

When Sol verification is explicitly enabled, developer instructions guide the primary model to verify meaningful manipulation checkpoints—such as approach, gripper closure, short lift, transport, placement, release, and withdrawal—combining adjacent phases where appropriate and stating why omitted phases do not apply, rather than leaving the tool unused. When Sol is disabled (the default), this verification guidance is omitted. Deterministic code never enforces a mandatory seven-step verification sequence or automatically generates or executes corrective actions.

Each verification request supplies the intended goal or expected outcome, before and after observation IDs, camera/ROI selections, executed action IDs, and an optional destination description. Sol inspects the permitted RGB views, measured robot state, and immutable action requests and receipts, returning visible evidence, a verdict (`met`, `not_met`, or `uncertain`), missing information, and corrective feedback. The caller's expected outcome is treated strictly as a hypothesis to be tested rather than established fact. Action receipt status and visual outcome are evaluated independently: a partially executed motion may still achieve a local visual objective, and a `completed` motion receipt never proves that an object was grasped or stably placed. Provenance mismatches cannot use stale images to certify a new action, and occluded outcomes remain `uncertain`.

Raw SDK requests and notifications, structured JSON responses, input image hashes, action and observation provenance, helper thread/turn IDs, and token usage are archived in the run store, and `operation_verification.py` and `codex_evidence_agent.py` are included in the run source hash and source archive. After receiving Sol's structured feedback, the primary model decides the next action; Sol never controls the robot directly.

CPU unit tests and local HTTP fixtures validate the integration without launching external APIs or physics simulation: the installed Codex CLI connects to a local loopback test server to verify primary-thread isolation, image and structured-schema delivery, targeted helper cancellation without disrupting the actor, shared budget accounting, automatic retries on explicit service errors, and deadline-free handling of slow responses. Closed-loop task impact must be evaluated in independent benchmark runs rather than inferred from software unit tests.
