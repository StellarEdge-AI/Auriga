# 模型主导操作：传输、风险参考与 Sol 验证

本页说明模型请求的传输策略、代码与模型的判断分工以及可选的 Sol 操作验证：模型响应不设本地截断期限，明确错误由harness自动重试；代码提供辅助计算，主要物体/接触判断由模型负责；Sol通过Codex官方agent接口验证操作，只接收必要证据，不继承主模型上下文。旧实验的冻结源码与结果不因这些修改回写。

## 模型请求

早期版本的90秒总响应期限是本地实现选择，不是API服务要求：它在独立HTTP worker的`communicate`上设90秒，直到整个HTTP流关闭才检查响应，失败后最多重试12次。在 RoboDojo 运行中观察到已收到HTTP200和首字节的请求被该本地期限反复终止；由于没有保存完整的中间流，无法判断上游是在持续生成还是等待关流。

当前`ModelRequestProxy`和独立`ResponsesClient`均为：

- 无请求总期限、无socket读超时。请求仍在等待时不会因耗时而重发。只有明确且可重试的服务错误触发harness自动重试，默认最多12次重试（首次加重试共13次HTTP尝试）。
- 收到完整SSE terminal事件即可完成，不等待HTTP连接EOF。只有完整可用成功响应可以交付工具输出并计入180次预算；失败/不完整响应不能执行其中的工具。
- HTTP 408/429/5xx、明确临时过载或server/rate-limit错误自动退避重试，优先使用正数Retry-After，否则沿用原阶梯与抖动。鉴权、非法请求、上下文/配额耗尽及拒绝等不可恢复错误直接报告。未知断线、缺少终态、incomplete或取消不按明确错误重发。失败尝试的工具输出不交付。
- 用户取消、停止和进程退出仍可中断请求。SDK request/stream retries为0；其配置没有无限idle sentinel，使用最大有符号整数毫秒与本地keepalive，实际不形成有意义的响应期限。
- 重试耗尽，或上游传输中断（`transport_incomplete`，如 `IncompleteRead`）后，代理按 `model.transport_recovery` 冷却（默认最多 10 轮：60/120/240/480 秒后每轮 600 秒，整局合计不超过 3600 秒；单次冷却低于 1800 秒的无进展超时）后重发同一请求体；Codex 只看到原请求的 keepalive，不新增 turn、提示或工具调用，模型上下文不变。RoboDojo 仿真在模型推理期间暂停，因此等待本身不改变世界；每轮冷却前后都由 Workbench 检查无执行中或 unknown 动作、无活动程序、仍接受动作且原生 episode 未结束，否则放弃恢复。证据为私有事件 `model.model_transport_recovery_scheduled`、`model_transport_recovered`、`model_transport_recovery_denied`（原因），以及 `runtime/model_requests.transport_recovery` 的轮数、恢复成功的调用数与冷却秒数；这些不进入模型可见内容。该恢复是对固定 RoboProbe 重试策略的扩展，`max_rounds=0` 回到原行为。
- 不可重试错误、恢复被拒绝或恢复用尽后，harness报告基础设施失败并收尾，不启动actor continuation。可重试错误恢复成功时继续原逻辑请求，无需人工解锁。运行中的保护改为连续30分钟所有来源均无实际活动；模型请求挂起或重试退避本身不豁免，真实网络传输持续推进则刷新活动时钟，不限制整次响应或整局总时长。
- `program_run` / `skill_run`（已删除）内的Sol调用也排除本程序等待该请求的时间，完成后恢复原剩余程序预算；其他程序或actor的等待不会增加它的预算。机器人动作超时、程序本地工作的时间限制和显式取消仍保留。旧skill每步额外预留90秒模型响应的做法已删除。

benchmark 和 `--exit-after-turn` 的运行监督聚合模型代理、Codex代码执行、机器人/仿真和程序的实际活动单调时钟。模型代理实时读取上游传输事件，不再等整次请求返回才记录阶段；真实上游字节刷新时钟，本地合成keepalive不刷新。全部来源连续1800秒无活动时，以 `runtime_inactivity_timeout` 取消请求并停止，保留未评分的基础设施结果；任何来源仍在推进就允许继续运行。`model_wait_seconds`仍供程序预算排除模型等待使用，不再豁免运行监督。原有环境初始化、单动作与程序本地工作期限仍独立保留。

下游连接意外断开按响应结果未知处理，锁住后续请求，不能借自动重连重发。显式取消也能打断尚未读完请求体的调用，释放其预算预留。SDK自身重试为0，只有harness拥有服务错误重试，避免两层重试叠加。

## 哪些判断由代码做

确定的执行契约保留：环境/观察身份、合法有限数值与四元数、动作内容一致性、单一动作写入者、停止状态、原生规划是否实际返回路线、缓存计划未消费且实测状态未过期。机器人固定模型、夹爪名义88.8mm开口、坐标变换、FK/IK运算属于计算工具。这些与未知物体的形状/重心/摩擦判断不同。

物体边界和持物体积来自模型在RGB与标定基础上的估计。碰撞审查把机器人连杆近似成球体、手指/物体近似成盒体或覆盖体，沿已计划关节路线计算位置并检查间隙与相交。固定采样、曲率保守界、裕量和接触规则可以报告风险，但不证明真实物理碰撞或不可行。

当前结果为`assessment_role=advisory`、`decision_owner=model`，状态`risks_detected`、`conditional`或`unavailable`；不再提供`execution_allowed`。主模型选择执行缓存计划、修改路线、改善几何估计或观察。直接姿态/多路点工具可用，不要求先preview。缺少新的grasp_plan也不会禁止闭爪。之前同一路线规划失败变为历史证据，不再直接拒绝模型有依据的重试。

当前接触参数仍可做诊断：

| 参数 | 保留的近似计算 | 当前意义 |
|---|---|---|
| `contact_entity_id` | 末端最终姿态附近60mm/20°的目标手指接触窗口 | 说明声明的目标接触；原始交叠仍保留，不授予执行许可 |
| `initial_contact` | 初始交叠的单调分离、保守曲率条件和末端脱离检查 | 未通过表示本次几何/分辨率没有证明分离，不等于撤不出来 |
| `placement_contact` | 持物对支撑顶部的名义几何，默认2mm、上限3mm容差 | 表示在该近似下能否支持放置解释，不限制模型实际选择的接触动作 |

`contact_overlaps`保留被上述分类解释的交叠对象、部件、时间和估计深度，不再用标签隐藏风险。审查或图像overlay失败时，已经生成的native计划保留并返回plan_id，同时说明评估未知；原生规划失败则没有路线可以执行。旧的八次只读门限已移除；任务级计划要求保持其现有实现，不由此处替换。

## “无法继续”的证据与提示

在 RoboDojo 运行中观察到，模型答复“无法继续”之前往往已尝试过修改姿态、垂直/横向撤手、细分物体代理、暂存、另一只手和推物；部分被放弃的抬升或撤手路线仅细化数值采样就能通过，也有在较早“无法继续”之后仍成功执行的情况。因此这类答复至多证明当前尝试受阻，没有证明任务物理不可行；反过来，也不能保证一定存在安全可行的恢复路线。

旧prompt已经提示短抬、空提后修改抓法、部分执行后读反馈和改变位置/朝向；旧completion hook主要催继续/回原位。当前保留新版本基于实测姿态的home判断，并加入明确恢复指导：辨认具体阻碍及实际尝试；区分本次搜索失败和全局不可能；按证据考虑另一抓点/方向/手臂/暂存/观察；避免无新信息重复拒绝；若仍无充分依据继续，明确报告尚缺什么证据。没有用固定坐标或动作配方代替主模型生成action。

遇到反复碰撞风险时，提示使用改变中间位置和朝向的分段接近/撤离，尝试绕开障碍。原生`robot_move_grasp.via_grasp_poses`最多7个中间姿态加最终姿态；`robot_execute_ee.action.path.waypoints`最多8个姿态（这两个旧工具已在 2026-10 重构中删除；当前 `robot_action` 一批最多 32 个阶段、每臂 16 个）。路线明确时可一次提交多点；中途反馈可能改变后续决策时使用分开的短action并逐段观察。多点单次action中间没有模型决策；仅把同一受阻直线切细不能产生避障间隙。

## Sol完整操作验证

默认`features.visual_review_model=null`，关闭`operation_verify`（已删除，现为 `vision_review` 的 `evidence_mode="operation"`）和`vision_review`；显式配置`gpt-6.1-sol`可重新开启。实现由Sol子代理完成，开启时运行时使用精确`gpt-6.1-sol`、high推理，通过共享传输计入actor/helper/compaction总180次预算。

动作前规划通过现有`task_plan`提示加强：先识别邻近物体对整臂、手指、持物及撤手路线的干涉；对陌生或不规则物体单独比较抓取区域、方向、稳定性和后续放置可行性；明确困难目标或容器内的物体最终位置、朝向、支撑、释放与撤手空间。模型按场景选择多段位置和姿态，并在需要新反馈的地方拆成独立动作。`grasp_plan`、`grasp_memory`（两者已删除）和轨迹预览仍是可选辅助，没有新增物体类别规则、固定操作顺序或执行门槛。

两个工具都固定触发`CodexEvidenceAgent`：使用已安装的官方Codex app-server和Python SDK，为每次调用启动独立的官方运行时，以`thread/start(ephemeral=true)`创建全新会话，再通过`turn/start(input, outputSchema)`提交证据并取得结构化JSON。每次调用独立，不fork、不resume主线程，不传主模型历史；使用空的专用工作目录、专门指令，不注册机器人动态工具。独立进程的全局配置关闭项目文档和记忆等后台特性；实际CLI的thread级feature覆盖不能可靠隔离这些特性，因此没有复用主模型进程。官方运行时仍可能附带固定的原生工具声明，本实现不改写官方请求来删除它们；提示只判断给定证据，若结果包含工具活动则不接纳。取消只中断本次helper，认证和180次计数仍复用harness现有代理。Sol专用的手写HTTP/SSE请求通道已删除，离线视觉probe也复用官方agent接口。

接口依据：[官方App Server文档](https://developers.openai.com/codex/app-server#start-or-resume-a-thread)区分新建thread与复制历史的fork，并支持turn级`outputSchema`；[官方Subagents文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)说明agent模型与上下文分工。本实现使用新建官方agent thread保证最小上下文，由现有验证工具确定性触发，无需主模型自行决定怎么spawn。

显式开启 Sol 后，主模型选择有意义的检查点：接近、闭爪、短抬、运输、放置、释放、撤手。指导要求覆盖实际操作结果，而不只是提供一个闲置工具；相邻动作可合并为检查点，不适用阶段说明理由。默认关闭时不注入这段验证指导。代码不强制执行固定七步序列，不自动生成或执行补救动作。

输入包含目标/预期结果、前后观察ID、相机/ROI、实际动作ID及可选目的地。Sol读取许可RGB、实测机器人状态、不可变请求与回执；输出可见证据、`met/not_met/uncertain`、缺失信息与补救反馈。预期结果只是待检验的说法，不是事实。回执失败/部分执行和图像结果分开：部分执行也可能达到某个局部视觉目标，反之completed也不证明夹住或放稳。来源不匹配不能借旧图片证明本次成功；遮挡保持未知。

原始SDK请求/通知、结构化响应、输入图片hash、动作/观察来源、agent thread/turn ID和用量一并存档；`operation_verification.py`与`codex_evidence_agent.py`包含在run源码hash与归档中。主模型收到反馈后决定下一次action，Sol不接管机器人。

相关验证采用CPU单元/本地HTTP fixtures，不启动真实API或仿真：真实已安装的Codex只连接本地HTTP测试服务，覆盖主对话隔离、图片与结构化结果、helper定向取消后actor继续、共享预算、明确服务错误自动重试及慢响应无本地期限。运行时闭环效果需要独立实验验证，不能从代码测试推导任务成功率提高。
