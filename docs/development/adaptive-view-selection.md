# Adaptive Camera Feedback

`images.feedback_policy` defaults to `all`. The opt-in `adaptive` policy filters which archived original RGB camera views accompany routine completed action and template feedback. Image capture and backend storage still retain all cameras. View selection is a deterministic CPU comparison that neither invokes a model nor advances the simulation.

Initial observations, deliveries following context compaction or session replacement, explicit `robot_observe` calls, historical view requests, waits, failed or uncertain action outcomes, observation checkpoints, and key handoff verifications always deliver the full set of camera views. A supported-transfer template context or an airborne-receiver template is treated as a key handoff, whereas routine completed templates are eligible for view deduplication. Explicit historical camera or crop queries always honor the caller's request, and unrecognized contexts fall back to full inclusion. Both direct actions and outer manipulation templates share the same selector; captures taken internally within a program never advance the primary model's delivery baseline.

All three cameras—including the head camera and both wrist cameras—are compared against the last full original view actually delivered to the model. Arm participation is recorded as telemetry rather than used as an inclusion or exclusion rule: a stationary arm's wrist view is included whenever its pixels change significantly, and an active arm's wrist view can be omitted if its image remains unchanged. If every camera view falls below the change thresholds, the response delivers measured proprioceptive state and retrieval metadata without repeating RGB images. Trajectory overlays follow a separate delivery policy: routine completed actions with full trace recordings return a scalar summary and an exact artifact reference, whereas diagnostic actions retain detailed paths and rendered overlays. A trajectory overlay never replaces the original-image baseline; see [Tool Output Contract](tool-output-contract.md).

## Delivery Baselines and Caller Contract

`auriga.perception.view_selection.select_observation_views(bundle, images, last_delivered, ...)` accepts archived observation metadata, a mapping from camera IDs to original image bytes, and a mapping from camera IDs to delivery baselines. It returns JSON-serializable `selected_camera_ids`, `skipped_camera_ids`, ordered per-camera `decisions`, active thresholds, and fallback reasons. Each skipped camera decision records the camera ID, current observation ID, baseline observation ID used for comparison, skip reason, and a complete `history_view_observation` tool call with pre-filled arguments.

`baseline_record(bundle, camera_id, rgb_bytes)` constructs an in-memory record holding the original encoded image bytes, image provenance, dimensions, calibration ID/reference, observation ID, and run/episode/environment identity. Because this record holds raw bytes, it is kept separate from JSON delivery metadata. The caller must update its baseline mapping **only when that full, uncropped original view is actually delivered to the model**. Raw captures, archived images, skipped views, program-only tool responses, and cropped, resized, or overlay views never advance the baseline. Baselines must be reset after model context loss, context compaction that discards historical images, session replacement, or any other event that invalidates the assumption that the model still holds the reference image in context.

The Harness also invalidates baselines synchronously whenever `contextCompaction` start or completion events fire on the actor thread. Because local window compaction may travel over standard `/responses` requests, monitoring `/responses/compact` alone is insufficient; the proxy endpoint hook serves as an additional fallback. Compaction on background helper threads does not reset the actor's visual baseline.

Running `select_observation_views` never mutates the baseline mapping itself. Consequently, gradual frame-to-frame changes accumulate against the last delivered image until a threshold is crossed; skipping a frame never shifts the reference forward. A full original camera view fetched via a history tool can become the new baseline once delivered to the model, whereas a cropped historical view cannot.

The caller provides `receipt_status`, `receipt_reason`, and `context`. Deduplication applies only when `context` is `post_action` or `template`, `receipt_status` is `completed`, and `receipt_reason` is absent or empty. An outer template qualifies as `completed` for view selection only when all of its expected phases succeed and its terminal observation is current (which makes no claim of physical object retention). Callers can pass a different context or set `force_full=True, full_reason="handoff_verification"` to force full multi-camera delivery. `active_arms` is retained as optional diagnostic metadata. Any unrecognized context, non-completed status, or exceptional reason conservatively includes all camera views.

The caller also verifies synchronized camera calibration and passes `calibration_valid={camera_id: True/False}`. Observation profile permission alone is not sufficient—only an explicit `True` permits baseline comparison. Missing or changed calibration references, unknown or changed environment identity, missing provenance, pixel transforms, altered image dimensions, missing image bytes, or decoding errors automatically force inclusion of the affected view. Matching encoded byte strings do not bypass image decoding, ensuring that corrupt inputs are still surfaced rather than silently skipped.

## Change Thresholds

All thresholds are exposed as module constants, can be overridden via the `settings` dictionary passed to the selector, and are echoed in the returned metadata. Invalid threshold overrides force full image delivery. The default thresholds are intentionally conservative:

| Metric | Include Camera View When |
|---|---|
| Mean absolute RGB difference on a `96 × 72` BOX-downsampled thumbnail (`0–255` channel scale) | `>= 1.0` |
| Fraction of thumbnail pixels whose maximum per-channel RGB difference exceeds `12.0` | `>= 0.001` |
| Maximum single-pixel, single-channel difference at full original resolution | `>= 32.0` |

Crossing any single threshold triggers inclusion. The full-resolution peak check catches small, high-contrast local changes that thumbnail averaging might otherwise smooth out. Comparisons run on decoded archived RGB pixels prior to transport re-encoding and never alter the resolution or pixel coordinates of views delivered to the model. Because this is a purely visual heuristic, sub-threshold differences can still be task-relevant, and benign rendering or compression noise can trigger inclusion; the thresholds carry no guarantee of semantic equivalence or task performance.

## Measurement and Validation Limits

Selected and skipped image counts and archived source bytes should be tracked separately from encoded transport bytes. Estimating omitted transport bytes with the same encoder yields a counterfactual delivery-volume metric, not a direct measure of model image tokens. Outbound model requests also carry conversation history, tool schemas, and text, and upstream cached-input tokens are accounted for separately by the provider.

The orthogonal `reuse_exact_images` feature deduplicates only byte-identical image parts within a single model request by replacing later duplicates in that same request with a reference to the first occurrence; it does not provide a cross-observation baseline across turns. Similarly, the in-memory data-URI cache saves CPU encoding time and hard-linked archive blobs save disk space, but neither reduces the number of visual views sent to the model.

CPU unit tests verify cumulative change detection against the last delivered baseline, sensitivity to small local changes, all-camera comparison (including changed active wrist views), failure and context overrides, deterministic camera ordering, retrieval tool-call metadata, and conservative fallbacks. These tests validate the view-selection logic in isolation. Any claim of preserved task performance or end-to-end cost savings requires a controlled full-feature ablation comparing `all` versus `adaptive` policies across native task scores, executed native steps, model token usage, and encoded transport volume. Offline replays over frozen trajectories can estimate omitted image counts and byte volumes, but cannot predict how omitted views would alter the actor's closed-loop decisions or establish causal episode-level savings.
