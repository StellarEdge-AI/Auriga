# Extending Skills, Plugins, and Tools

Extensions start from concrete use cases and authority boundaries. First confirm whether existing tools can be composed to solve the problem before deciding where to make changes. [AGENTS.md](../../AGENTS.md) is the entry point for development rules, [Architecture](architecture.md) explains state ownership, and the [ToolSpec Guide](tool-plugins.md) provides executable templates.

## Choosing the Right Layer

| Goal | Recommended Entry Point | Required Constraints |
| --- | --- | --- |
| Improve model operational experience, applicability conditions, or failure recovery | `task_notes.py`, `operation_memory.py`, and [Task Notes](task-notes.md) | Specify conditions, evidence, and counterexamples; reusable methods must not smuggle evaluation answers or hidden state. Cross-task shared records must use existing scopes. |
| Multi-step feedback loops or numerical computation programs | `program_run` / `auriga_client.py`, following [Program Result Semantics](program-result-semantics.md) | Call tools through the broker with physical review enabled by default; `stdout` is not execution evidence, and nested program launches cannot bypass permissions. |
| New general computation, query, or physical capability | `ToolSpec` under `auriga/runtime/tools/plugins/`, explicitly injected at the application assembly point | Share the same schema, role, effect, availability, typed output, and restricted context; see the workflow below. |
| New action representation, backend, or planning implementation | [Unified Actions](unified-actions.md) and [Robot Backend Boundaries](robot-backend-boundaries.md) | Preserve the single execution entry point, truthful capability declarations, cached trajectories, and identity/budget/stop/uncertainty semantics. |
| New robot arm, simulation platform, or real-hardware environment | [Robot and Environment Integration](robot-environment-integration.md) | Separate implementation by responsibility; runtime execution must match a validated environment/model combination; registering documentation does not replace control adaptation. |
| Legacy manipulation/depth skill maintenance | `skills.py` (removed), `depth_skills.py` (retains only the `skill_help` catalog for `depth_query`), and corresponding tests | These are historical templates and motion helper libraries, not a separate tool catalog for new actors; do not re-expose legacy public entry points. |
| Instructions or workflow docs for development agents | Root `AGENTS.md` and topic guides in this directory | Explain trigger conditions, contracts to read, modification targets, validation, and delivery; the primary Codex session does not inherit host skills, MCP servers, or plugins; the OS sandbox is disabled by default (see the code execution sandbox section in [Configuration](configuration.md) for permissions when isolation is enabled vs. disabled); these are managed separately from Harness `ToolSpec` plugins. |

The repository currently has no generic `SKILL.md` discovery mechanism or automatic external plugin installer. Maintain development documentation through the entry points above. When packaging an agent skill for a host distribution is strictly necessary, specify the host format, resource paths, and installation method separately while reusing the contracts defined here rather than inventing a new runtime loader.

## End-to-End Workflow for Developing a Tool

1. Search for similar handlers, all callers, and existing tests. Determine the inputs, output `kind`, formal evidence read, side effects, and failure behavior. Keep pure computation in existing domain modules and keep public handlers thin.
2. Write the `ToolSpec` following the [read-only tool template](tool-plugins.md#adding-a-read-only-tool), explicitly declaring `roles`, `effect`, `api_version`, and `output_schemas`. Reject extra fields, invalid types, and non-finite numbers at input validation; leave cross-field or current-observation checks to the existing semantic owner.
3. Register the tool at the assembly point via `Workbench(..., tool_specs=[...])`. For new built-in tools, update `definitions.py`, `handlers.py`, and `builtins.py` together. Do not add duplicate name branches across Harness, the program broker, and the catalog. When a tool lacks required capabilities, the catalog and invocation path must report the same unavailability reason.
4. Every model-visible field must serve a clear purpose for current reasoning or the next tool call. Strip non-essential metadata at the producer, keep hashes in internal archives only, and let the shared presentation layer generate short IDs for necessary object references. Have the handler return `ToolOutput(...).response()` or an explicit `ToolResponse`. Put structured facts in `data` and compressible descriptions or images in `content`. Use existing intra-run references for domain IDs rather than parsing strings to guess result types.
5. Add regression tests for both entry points: live `Harness.handle_tool` and the program broker (broker permissions and review remain enforced regardless of the sandbox switch). Assert that invalid inputs do not invoke the handler or produce physical actions, that permission/disabled/capability failures are rejected at the entry boundary, and that output contract failures preserve actual execution facts.
6. Update documentation, positive/negative examples, and test pointers, then run the affected checks per the [Validation Guide](validation.md). Increment `api_version` when input or result semantics change incompatibly; schema hashes only track structure and do not replace semantic versioning.

`tests/test_tool_registry.py` already includes runnable examples covering read-only plugin calls from both entry points, physical authorization, single-writer and idempotency guarantees, output contract violations, and actor provenance filtering. Extend those tests first rather than creating a separate demo framework.

## Additional Requirements for Physical Plugins

Only invocations with `effect="physical"` receive `context.execute`. It binds correlation metadata and generates a deterministic `action_id`; pass a request conforming to the existing action contract so Harness can verify identity, observation version, budget, and immutable payload. Never persist receipts yourself, fabricate `completed` statuses, or bypass backend stop acknowledgements.

Additional physical plugins called from a program require `allow_direct_actions=true` on that `program_run` invocation; built-in `robot_action` and `robot_wait` use the existing pause-and-review workflow. If an extension does not yet support program review, expose it only to the `actor` role. Because a trusted Python host can still capture external services in closures, `ToolContext` is not a sandbox against malicious Python; code review must verify that the declared `effect` matches actual behavior.

Construct the typed response corresponding to the persisted execution result before assembling optional images, plots, or text. Delivery errors after physical execution has occurred must follow the existing output-contract path: return the original receipt and forbid automatic replay. In program evidence, `action_id` may come from `request.action_id`; do not assume the receipt always duplicates the ID. Test idempotency for both "same ID with identical payload executes once" and "same ID with different payload is rejected," and verify that replaying an older checkpoint receipt does not overwrite the latest plan.

## Writing Operational Experience and Documentation

A useful operational note specifies: applicable visual and robot conditions, action intent, what to observe, how to recognize failure, recovery or stopping criteria, and the run/action/observation evidence supporting it. Separate generalizable advice from single-episode anecdotes, and never state a single success as a guarantee across all layouts. Parameter units, coordinate frames, TCP conventions, orientation order, and gripper semantics must follow the shared contracts.

Documentation for development agents must reference real code paths, runnable commands, and explicit evidence boundaries. Keep active rules in long-lived guides; dated experiment or review reports should preserve the revision and results from that time, adding links for subsequent fixes rather than rewriting past failures as passes. After updating entry points, synchronize `README.md` and the documentation index so specifications do not diverge into conflicting copies.
