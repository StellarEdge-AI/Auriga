# Tool Registration, Execution Boundaries, and Extensions

The model catalog, live actor tool calls, and the program broker all read `ToolSpec` declarations from a single `ToolRegistry`. Adding a tool only requires registering its handler—without adding branches to `Harness.dispatch`, the Workbench allowlist, or the program allowlist. Existing declarations, public handlers, and legacy adapters live in `auriga/runtime/tools/definitions.py`, `handlers.py`, and `legacy.py`, respectively, while `builtins.py` assembles built-in tools into the runtime registry.

Each declaration contains `api_version` (defaulting to `"1.0"`), the input JSON Schema, `output_schemas`, the handler, allowed `roles`, the side-effect classification (`effect`), and an optional unavailability callback. `output_schemas` maps each permitted `ToolResponse.kind` to a JSON Schema validating its `data` payload; when a tool can return multiple result kinds, declare each `kind` explicitly rather than guessing types from display text. New `actor`/`program` plugins must provide this declaration explicitly. Registration validates the input schema, output schemas, and their root-level positive `examples`; invocation validates the actual typed result returned by the handler. Versions must follow `major.minor` format with a positive integer `major` and a non-negative integer `minor`.

Each `ToolSpec` corresponds to a Codex native function: the declaration must include `type="function"`, a string `name`, a string `description`, and `inputSchema`. Matching native `0.160` admission checks, `name` must be 1–128 ASCII letters, digits, `_`, or `-`, and must not start with `mcp` or `mcp__`. Legacy `namespace` / `exposeToContext` fields are rejected. The optional `deferLoading` field must be a boolean: omitting it or setting `false` publishes the tool directly, whereas `true` places it into the `auriga` namespace via the Codex adapter for on-demand discovery. The registry and program calls still use the original function name without introducing a second handler routing table. Root-level singleton `null` input schemas are also rejected by native admission. At registration time, the registry checks JSON representability across the entire declaration, these native fields, and known admission constraints before validating live inputs against the local JSON Schema; it does not impose Responses `strict` mode or MCP-specific fields. Because the native backend lowers and compacts input schemas, local schema validation does not claim that every JSON Schema keyword survives unchanged in the model request. Registration stores independent snapshots of the declaration, input/output/legacy schemas, and roles; mutating the original `ToolSpec`, the return values of `spec()` / `validate()`, the catalog, the manifest, or `_specs` inspection copies in the host will not alter the live contract. `validator_for()` likewise returns an independent validator without exposing shared mutable cached schemas. To change the behavior or declaration of a registered tool, build a new registry and corresponding session.

Parameter meanings, units, defaults, numerical bounds, and applicability conditions are part of the tool contract. Types and hard constraints belong in `inputSchema`, while field `description` strings explain domain semantics and invocation conditions. Public tools generate an input field guide inside the top-level `description` from the same input declaration, preserving field descriptions and constraints that native schema lowering might strip—without gating on a 5,000-byte size threshold. Conditional branches must state their applicability conditions rather than unconditionally merging `required` lists, types, or bounds from mutually exclusive branches. Examples are still published solely from their original example sources. Verify actual delivery field-by-field using loopback Responses tests against the real bundled `app-server` rather than assuming a field present in the Python catalog reaches the model.

Formal geometry requests in `geometry_query` and measurement/target requests in `depth_query` publish their respective exact field types. The legacy RGB-D compatibility forwarding in `geometry_query` lists only the explicitly supported depth kinds and points to `depth_query` for the full contract rather than duplicating the depth parameter manual; compatibility payloads are still validated by the same `DepthRuntime` and cannot be used to pass arbitrary unknown kinds or bypass RGB-D availability checks.

The `pixel_plane` branch of `geometry_query` accepts a single `observation_id`, `camera_id`, original-image pixel `pixel:[u,v]`, and required `plane_origin_m:[x,y,z]` and `plane_normal:[nx,ny,nz]`. It returns the conditional intersection `point_m` (`status=conditional`, not measured depth), the 3D sensitivity vector `d_point_d_normal_offset_m` for a +1 m offset along the plane normal, and cross-camera reprojections `cross_camera_projections` onto other calibrated cameras from the same frame. The optional `plane_origin_alt_m:[x,y,z]` computes a second intersection on a parallel plane with the same normal and returns `alternate_point_m`, `alternate_ray_distance_m`, and `assumption_delta_m`; the optional `target_camera_id` returns a projection overlay image on the target camera in the same call. Prefer `triangulate` when a feature is visible and matchable across two views; use `pixel_plane` when occluded in one view or when the target lies on a known support plane, verifying against cross-camera projections. When the absolute dot product between the ray and unit normal is less than `0.01`, or when the intersection lies at or behind the camera origin, the tool returns `unknown` with `value=null`. See `tests/test_geometry.py` for regressions.

The input guide is delivered as part of the tool definition itself, not as an extra system message or per-turn injected prompt. Ten tools are directly visible: `task_plan`, `robot_action`, `robot_observe`, `program_run`, `operation_memory`, along with the frequently used `geometry_query`, `history_view_observation`, `robot_wait`, `robot_contact_overlay`, and `history_list_actions`. The remaining 10 built-in tools set `deferLoading=true` in their declarations and are loaded in full after discovery via native `tool_search`. The active catalog is still filtered by role and runtime configuration; deferred loading never re-exposes disabled or unavailable tools. Directly visible tools were selected based on primary model call frequency and case/task coverage in historical runs, with internal program calls counted separately. Because schemas returned by `tool_search` still undergo native simplification, on-demand loading does not replace description and constraint preservation. Tool search does not advance the physical environment, though it incurs tool interactions and follow-up model requests that count toward existing model request budgets. Invocations continue to check role, availability, input, and output through the same registry; native network tool restrictions remain unchanged, and no new search service or configuration toggle is introduced.

A frozen catalog supports native thread resume. Changing `deferLoading` counts as a catalog change, and the existing `resume_tool_registry_conflict` check rejects mismatched configurations before launch. Older flat-catalog threads can be resumed using their original catalog; a newer catalog must not be silently applied to an old thread. The current native SDK `thread/resume` RPC does not accept a parameter to replace `dynamicTools`.

`history_list_actions` accepts an optional `anchor="events"|"failures"|"gripper_commands"|"all"` to retrieve interaction slices from the current episode on demand. It returns a top-level summary (`selected_count`, `episode_action_total`, `status_counts`, `execution_issue_count`, `gripper_command_count`, `evidence_gap_count`, `next_start`) alongside compact interaction blocks (containing action identity, typed request/receipt evidence, `observation_ids.decision/execution_start/result`, `measured_delta` from execution start to result frame, gripper command positions, and explicit `evidence_gaps`), plus a `full_result` handle to read the raw request/receipt by action ID. Omitting `anchor` preserves the original paginated index and `detail="full"` complete-list semantics; `detail="full"` cannot be combined with `anchor` or pagination arguments. See [`history_output.py`](../../auriga/core/presentation/history_output.py) for the implementation and `test_history_output` / `test_tool_registry` for regressions.

This design follows patterns from [Codex's built-in shell tool](https://github.com/openai/codex/blob/main/codex-rs/core/src/tools/handlers/shell_spec.rs), where the parameter description for `yield_time_ms` explicitly states its default value, unit, and range—text that survives intact in live requests under our pinned version. Similarly, the [MCP SDK parameter description tests](https://github.com/modelcontextprotocol/python-sdk/blob/main/tests/server/mcpserver/test_parameter_descriptions.py) verify that `list_tools` parameter schemas preserve `description` fields, and its [constrained parameter tests](https://github.com/modelcontextprotocol/python-sdk/blob/main/tests/interaction/mcpserver/test_tools.py) generate both schemas and runtime validation from `ge`/`le` definitions. Auriga achieves the same guarantees using its existing JSON Schema and `ToolRegistry` without introducing an MCP server or swapping validation frameworks. For dynamic tool interfaces, see also the [app-server reference documentation](https://www.codex-docs.com/docs/app-server); where version differences exist, the pinned SDK and native loopback tests are authoritative.

`catalog(runtime)` and `invoke(..., role=...)` share the exact same availability check. At the entry boundary, `invoke` first rejects disabled or unauthorized tools, then performs full input schema validation and request-specific capability checks before calling the handler. Unknown parameters, booleans masquerading as numbers, and non-finite floats never reach a public handler. Underlying semantic owners remain responsible for cross-field constraints such as observation versions, native action budgets, and cached plan states. Native backends explicitly declare `unified_action.available`; legacy adapters lacking this field retain compatibility interpretation for `resampled` configurations. New backends must declare accurate capabilities and implement the corresponding ports rather than relying on omitted fields to imply validated support.

`ProgramRunner(harness.program_services())` receives only a frozen `ProgramServices` bundle: server-bound callbacks for tool validation, invocation, and `effect` lookup, observation snapshots, active-action query and cancellation callbacks, and the run's `Store`. The runner holds no direct reference to `Harness`, `robot`, or `ToolRegistry`. The `actor` role is bound by `Harness.handle_tool` and the `program` role by the server-side callback in `ProgramRunner`; callers cannot escalate their role via JSON arguments. `Harness.dispatch` serves as the `trusted_legacy` adapter entry point for existing Python integrations (legacy motion and `scene_*` tools were removed in the 2026-10 refactor). Legacy adapters retain their original semantic checks and cannot be used by actors or programs to bypass unified actions or primary-model review. The historical `from auriga.runtime.harness import TOOLS` compatibility alias was removed along with the legacy tools.

## Adding a Read-Only Tool

For existing opt-in plugins that read formal observations through narrow owner callbacks, see [Robotic View Solver](robotic-view.md) and [Stereo Epipolar Guide](stereo-guide.md); both reuse the same `actor`/`program` registry and deliver usage instructions through their respective `ToolSpec` definitions.

Place the declaration below under `auriga/runtime/tools/plugins/` (for example, `example_status.py`), import it at the application assembly point, and pass it to `Workbench(..., tool_specs=[make_status_tool()])` (hosts instantiating `Harness` directly also accept `tool_specs`). The handler receives a `ToolContext` whose read-only action port returns raw action records from the current run without exposing the robot instance or raw `Store`.

```python
from auriga.core.tool_output import ToolOutput
from auriga.runtime.tools.registry import ToolSpec


def make_status_tool():
    def read_status(context, arguments, correlation):
        # Fixed read-only port; does not grant arbitrary path, observer artifact, or database access.
        receipt = context.read_action(arguments["action_id"])["receipt"]
        return ToolOutput({
            "action_id": arguments["action_id"],
            "status": receipt["status"],
            "reason": receipt.get("reason"),
        }).response()

    return ToolSpec(
        definition={
            "type": "function",
            "name": "example_action_status",
            "description": "Read a saved action status without executing it.",
            "inputSchema": {
                "type": "object",
                "properties": {"action_id": {"type": "string", "minLength": 1}},
                "required": ["action_id"],
                "additionalProperties": False,
            },
        },
        handler=read_status,
        roles=frozenset({"actor", "program"}),
        effect="read",
        api_version="1.0",
        output_schemas={
            "data": {
                "type": "object",
                "properties": {
                    "action_id": {"type": "string", "minLength": 1},
                    "status": {"type": "string", "minLength": 1},
                    "reason": {"type": ["string", "null"]},
                },
                "required": ["action_id", "status", "reason"],
                "additionalProperties": False,
                "examples": [{
                    "action_id": "action-example",
                    "status": "completed",
                    "reason": None,
                }],
            },
        },
    )
```

Positive and negative output examples for this template can be checked directly with the same validator, and registration automatically validates `examples` without maintaining a separate example table:

```python
from auriga.runtime.tools.registry import ToolRegistry, validator_for

spec = make_status_tool()
ToolRegistry([spec])
check = validator_for(spec.output_schemas["data"])
assert check.is_valid({"action_id": "action-example", "status": "completed", "reason": None})
assert not check.is_valid({"action_id": "action-example", "status": True, "reason": None})
```

The `scene_` prefix is reserved for legacy adapters and cannot be registered as an `actor`/`program` plugin; registration rejects it immediately so the catalog never advertises a name that the entry point will refuse. Because `tool_specs` are added to the registry before `Harness` initialization, `features.disabled_tools` can reference plugin names, and duplicate names fail immediately. Workbench's runtime source archive recursively collects in-package Python files under relative package paths such as `runtime/tools/plugins/example_status.py` (with `Harness` archived under `runtime/harness.py`). The launch manifest's `tool_catalog` records the catalog hash, each tool's `api_version`, input schema hash, `result_kinds`, full `output_schemas` and their hashes, `effect`, availability, and unavailability reason. `api_version` is the author's explicit compatibility version for tool behavior and result semantics, whereas schema hashes identify structural shape—a behavioral change may require bumping `api_version` even when the schema is unchanged, so neither replaces the other. The catalog hash covers the delivered name, description, and input schema; the output contract hash is frozen separately without expanding Codex's input tool catalog. Older manifests lacking `api_version` or output contracts remain marked unknown rather than backfilled with current defaults. Source files from external packages are not automatically included in the Auriga package source archive and must be recorded separately by the host; keeping declarations shipped with the project inside the package is sufficient.

No module scanning, dynamic download/install, or separate plugin service is needed. For an existing `Harness` instance, you can also call `harness.tool_registry.register(spec)` explicitly before starting the actor session; registering tools after the session catalog has already been delivered will not dynamically update the client.

## Side Effects and Program Authorization

`effect` can be either a fixed string or a callable returning a classification based on validated arguments. For `robot_action`, `preview` has effect `plan`, `inspect` has `read`, and `execute`/`direct` have `physical`. For `task_plan`, reading is `read` and saving is `record`. Operational memory distinguishes `read`, intra-run `record`, and cross-task `shared_memory`. Effect classifications describe domain side effects; routine logs or evidence artifacts created during read-only queries do not constitute physical actions.

`program_run` reviews physical actions by default. Built-in `robot_action` and `robot_wait` use the existing pause/resume review flow; additional program tools declared as `physical` can only execute if that `program_run` invocation was launched with `allow_direct_actions=true`—a plugin cannot bypass review simply by using a new tool name. Physical plugins requiring custom review workflows should initially expose only the `actor` role. `program_run`, `program_status`, and policy actions do not expose the `program` role, preventing programs from nesting sub-programs or escalating privileges through legacy entry points.

By default, plugins receive only `ToolContext` identity metadata, snapshots of current observation/capabilities/budgets, and `read_action`. Only `physical` invocations receive `execute(action)`, which forwards the broker correlation and assigns deterministic `action_id` values in call order within the tool invocation, routing actual execution through `Harness.execute` for state, budget, immutable payload, and idempotency checks. Neither the native `robot` backend nor raw database handles are exposed. Built-in history handlers explicitly bind their runtime dependencies at assembly time. Availability callbacks receive a separate frozen `ToolAvailability` containing only configuration, capability, and service-readiness facts.

Trusted Python code is still not a sandbox against malicious host code: additional services captured in closures by the host remain the host's responsibility. Plugins must faithfully honor their declared `effect` and never fabricate execution receipts; standard extensions should use the narrow read and execution ports described above.

## Internal Types and External Wire Replies

The external wire format remains `{success, contentItems}`. Internally, `ToolResponse` is a distinct non-mapping type holding `kind`, raw `data`, `success`, and separate `content` presentation items without implicitly serializing JSON on read. `ToolOutput(summary).response()` wraps `StructuredText(summary, projection="data")`. When presentation and execution facts differ, return `ToolResponse([StructuredText(display, "action_display"), ...], data=original, kind="action")` rather than substituting raw execution data for display text. Post-action observations are attached as separate content items, and program status vs. raw job records—or observation bundles vs. delivered metadata/images—are likewise stored separately.

Standard plugins default to `projection="data"` rather than guessing domain result types from JSON shape. At final actor delivery, valid IDs and artifact references are replaced with stable intra-run short references, and provenance is recursively stripped: hash/digest/checksum/fingerprint fields, source URLs/files/repositories/commits, document source sets, and hash-shaped `version` or `calibration_id` strings. Ordinary numeric revisions, `solver_version`, and similar domain values are preserved, and `image_url`/`audio_url` remain intact for media delivery. This filtering applies to both root and nested plugin fields, so plugins must not rely on filtered provenance fields to carry essential domain data to the actor. Program presentation and historical result replay apply the exact same filter, while typed `data` and raw observer archives retain all facts. Producers needing built-in summaries explicitly select named projections such as `capabilities`, `action_result`, `action_display`, `observation`, `operation_review`, or `contact_overlay`; `action_result` preserves the domain owner's full/summary structure without applying a second field-allowlist truncation to the receipt. Projection names govern presentation only and do not alter the trusted execution semantics of `ToolResponse.kind/data`.

Actor outputs are projected and serialized at the final delivery boundary in `ActorOutput.present`, while program file-descriptor replies apply the same metadata filtering and short-reference resolution in `ActorPresentation.present_response`. Artifact persistence of raw wire replies, logging, and explicit legacy calls generate plain JSON via `wire_response` / `wire_content`. `ToolOutput.content_items()` serves purely as an explicit wire-compatibility adapter. Reading historical wire/artifact/log records may retain legacy display cleanup, but those records must never be parsed backward to infer internal execution facts. Direct Python callers needing wire format should adapt explicitly rather than relying on internal dataclass serialization details.

Built-in tool output declarations first constrain existing result envelopes: `action` requires an object `receipt` with a string `receipt.status`, leaving full action, trajectory, execution counts, and state transitions to their domain owners; the registry neither duplicates a second physical contract nor re-infers whether execution completed. `plan` validates status fields and permits failed previews without a `plan_id`, while program review continues to require an executable cached plan. `observation` validates the bundle delivery envelope already verified by the shared observation contract. `history_list_actions` supports both paginated objects and full lists; `history_read_trace` preserves the archived JSON shape (which may be an array, scalar, or `null`), requiring only valid JSON without imposing extra structural restrictions on historical traces. Other `data` built-in results currently validate the top-level object container while leaving deep optional fields to their existing domain owners and regression suites; this container check does not claim that full field-level output schemas have been published for every legacy payload.

Display-only compatibility explicitly permits `null`: `history_view_observation` and `robot_contact_overlay` carry `data=None`, and action/trajectory inspection in `robot_action` may likewise return display items only with `data=None`. The broker never treats such responses as actions or fresh observation evidence. Other `robot_action` modes return `plan` or `action` and are validated against the corresponding `kind` schema. Only legacy adapters restricted exclusively to the `trusted_legacy` role may set `output_schemas=None` (recorded in the manifest as `trusted_legacy_wire_unvalidated`); new `actor`/`program` plugins cannot use this exemption.

An output contract violation occurs after the handler has already returned. Rather than raising an input error, the registry preserves the original `kind/data` and serializable display items, returns `success=false`, and appends an `output_contract_error` with `phase=after_handler` and an instruction forbidding automatic replay. Persisted `completed`, `partial`, or `stopped` receipts remain intact; execution outcome is `unknown` only when a trusted typed receipt is missing. The program broker increments its output-error counter while still recording actual execution facts from the original receipt. Here, `success=false` indicates a response contract failure, not that the physical action failed to execute. Non-JSON values or display items violating native content-item shapes are quarantined while valid items are still delivered, without calling `repr()` on invalid objects or replaying the action; `action` responses also attach a serializable summary of the typed receipt facts. Content items must be `StructuredText` or native `inputText/text:string`, `inputImage/imageUrl:string`, or `inputAudio/audioUrl:string` items—arbitrary JSON scalars or objects are not valid native content items. Malformed native items report `invalid_native_content_item` with the exact `/content/<index>/<field>` pointer, and any other output error also strips invalid items. Actor projection failures preserve the same post-execution error semantics. Outer `success` must be a true boolean; integers, strings, `None`, or non-JSON objects produce a `/success` after-handler diagnostic rather than downgrading a response-contract error into execution `unknown`. The registry validates outer types, JSON representability, native content items, and declared schemas before generating JSON text.

When a handler assembles optional observations, images, or detail artifacts after physical execution has already occurred, it must also guard against delivery exceptions: preserve the typed `action` facts first, then reuse `output_contract_error` to return `action_feedback_unavailable` so an exception never turns into a receipt-less generic tool failure. The unified action, wait, and policy handlers all cover this path. Idempotent replay of an older checkpoint must not write historical revisions or cursors back into the active plan.

The program broker's review flow, action summary, and latest observation tracking read cached plans from `kind="plan"`, raw `{receipt, ...}` payloads from `kind="action"`, and `ObservationBundle` instances from `kind="observation"`. It never parses `inputText` to recover internal execution facts; corrupted display text, field compaction, or spoofed `stdout` cannot alter trusted state. If only an external wire dict is present without an internal action result, execution counts and outcomes remain `unknown`—never backfilled with zeros or upgraded to success. Action IDs are taken from the receipt first and fall back to the original request if omitted, never parsed from display text. Full wire replies are still saved as observer artifacts for replay, not as unfiltered fallbacks readable by the actor.

See `tests/test_tool_registry.py` for regressions covering: invoking new read-only tools from both the live actor entry point and isolated Python programs; zero handler/action side effects on invalid input; output schema declarations and positive/negative examples; output schema hashes; preserving original receipts without replay when output violations occur after action completion; keeping missing receipts as `unknown`; configuration/profile/backend availability matrices; verifying spoofed display text cannot alter broker evidence; and recursive source archiving. `tests/test_program_review.py` additionally covers live process pausing, review, cache invalidation on world advancement, and unknown execution outcomes.

Targeted regressions in `tests/test_typed_actor_output.py` also verify: internal presentation without premature serialization or parsing, named mixed replies, domain field preservation alongside recursive actor provenance filtering, metadata fallback synchronization, post-execution display failures, and post-save program replay.

Context budget is a first-class interface constraint: non-essential metadata should be omitted at the producer. The presentation layer also strips hash fields, unnamed bare hashes, and checksum fragments in free text without inserting verbose placeholder text. Essential `action`, `job`, `review`, `observation`, `plan`, and `artifact` IDs use stable short references from the same `Store`—including composite IDs, dictionary keys, and references in program source code—and are resolved back to original identities at both entry boundaries. Bare hashes extracted via JSON Pointer, `stdout`/`stderr`, error strings, and text artifacts follow the same rules, while image and audio bytes are preserved unchanged. Output schema properties and `required` lists must not be broken by field filtering; hash-shaped enums that must be round-tripped use reversible short references while internal validation continues to check original values.

At the program execution entry point, only necessary object references in source code are normalized to the short references used in tool replies so source literals and tool responses can be compared directly; free-text scrubbing is never applied to executable source code. Ordinary code, checksum literals, and numeric constants remain untouched, idempotency checks use original call arguments, and the source archive records the exact executed code. See `tests/test_tool_registry.py` for live `program_run` reference, source, and replay regressions.

Auxiliary visual review filters structured evidence before serialization, and `CodexSession` filters readable text again on outgoing `/responses` and `/responses/compact` requests, covering resumed history. Native call/item IDs, media URLs/data, and encrypted reasoning tokens retain their exact protocol values without being expanded as display text. Internal verification hashes, idempotency digests, and provenance audits are never deleted by presentation rules. Tests should capture actual loopback HTTP or helper-turn payloads rather than only testing a standalone formatting helper.

## Structured Results for Generated Programs

`AurigaClient.call()` returns `success`, `kind`, `data`, and compatibility display `contentItems`. Generated programs consume `data` keyed by `kind`: action receipts live at `data.receipt`, while plans and planning rejections live in `data` under `kind="plan"`. `ToolOutput.projection` selects the domain data projection simultaneously; producers constructing `ToolResponse` directly use `data_projection` to explicitly select the corresponding metadata projection rather than guessing from display text or tool names. Everything then passes through `ActorPresentation` for metadata filtering and short-reference resolution. Public output `data` must still obey observation permissions and output schemas, and must never expose hidden internal state.

`kind="untyped", data=null` preserves the uncertainty of legacy display-only results, while `kind="error"` on exceptions reports invocation diagnostics only without inferring whether physical execution occurred. An `output_contract_error` on an already executed action does not alter the original receipt and must not trigger a resend. Idempotent replay of cached legacy results does not parse text to fabricate domain facts. For examples and regressions, see [Program Result Semantics](program-result-semantics.md), `tests/test_program_review.py`, and `tests/test_actor_presentation.py`.
