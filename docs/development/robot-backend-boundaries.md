# Robot Backend and Action Compilation Boundaries

The backend architecture preserves RoboDojo's execution semantics while cleanly separating pure data validation, ARX action compilation, subprocess IPC, and native simulation operations. Every physical action is still admitted exclusively through `Harness.execute`; plugins never receive a direct write channel to the worker.

Environment initialization is managed by `robot/backends/robodojo/environment.py`, and robot control identifiers and environment asset bindings live in `embodiments.py`. `robot/backends/factory.py` selects the environment constructor, while `action_compilation.py` routes public actions to the active backend's compilation and validation entry points; native execution in RoboDojo remains restricted to registered ARX X5 bindings. For the full list of integration files and adaptation requirements, see the [Robot Arm and Environment Integration Guide](robot-environment-integration.md).

| Module | Inputs and Outputs | Responsibility |
| --- | --- | --- |
| `action_validation.py` | Action payload + optional capabilities → validation result or error; dual-arm action → per-arm projections | Pure structural and numeric validation without importing runtime instances, backends, or renderers (`contracts.py` and `motion_speed.py` retain legacy import aliases). |
| `arx_contract.py` | ARX end-effector or joint-prefix request → selected arm and target or error | ARX frame/TCP conventions, joint-prefix dimensions, and native numeric constraints; never spawns a worker. |
| `arx_actions.py` | `kind, args, identity, capabilities` → canonical action request | Compiles move, grasp-reference, gripper, wait, and dual-arm requests; neither reads Harness state nor executes motion. |
| `proxy_contract.py` | Caller-supplied obstacle and held-object bounding boxes → normalized proxy estimates | Validates geometric proxy inputs without importing forward kinematics, image renderers, or simulation scenes. |
| `robot_process.py` | Worker command/environment + JSONL requests → progress/replies/cleanup report | Owns the worker subprocess, IPC pipes, cancellation channel, and exit confirmation; preserves `unknown` on timeout without replaying actions. |
| `robodojo.py` | Runtime config + typed operations → worker requests | Assembles the RoboDojo launch command, validates backend requests, serializes operations, and manages resets. Subclasses the process owner while preserving legacy `RobotBackend` imports and diagnostic attributes. |
| `worker_protocol.py` | JSONL stdin + adapter factory → JSONL stdout | Reader thread receives requests and cancellation signals only; all adapter calls run on the native main thread. Terminates the process on owner EOF. |
| `execution_evidence.py` | Receipt, segments, attempt/completion signals, measured samples, and counters → execution evidence | Independently aggregates `attempted`/`completed`/`uncertain` states, dual-arm segment records, and the three step counters per action without reading or writing the simulator. |
| `robot_worker.py` | Validated request → planning / native actions / measurements & receipt | Owns Isaac Sim, RoboDojo, and the native evaluator, keeping public observations strictly separate from observer-only evidence. |

A new backend implements `start`, `observe`, `execute`, `reset`, and `close`, plus capability-dependent methods such as `preview_batch`. `validate_action` serves as the backend's own numeric constraint gate: `Harness` first enforces shared checks—identity, generation, current observation, permissions, and budgets—before delegating to the backend validator. When an unknown backend lacks a capability, the system must reject the request rather than silently falling back to ARX conversions or execution paths.

`compile_action` accepts `kind` values `"move"`, `"grasp"`, `"gripper"`, and `"wait"`, while `compile_dual_action` explicitly takes parameters for both arms. Legacy tool names are mapped only at Harness's compatibility adapter boundary, whereas modern `robot_action` batch compilation calls these pure data functions directly. Caller-supplied units, TCP offsets, gripper phases, speeds, and stage dependencies retain their exact semantics.

A backend `reset` spawns a new worker only after confirming both `process_exit_confirmed=true` for the previous worker process and `reader_exit_confirmed=true` for its reader thread. Each reader thread is bound to the specific process, log file, and generation created at launch; if a blocking callback has not yet exited, its resources remain quarantined so a stale generation can never deliver a reply or write a disconnect state into the new worker. A missing terminal observation after an action invalidates the current observation pointer without altering already confirmed completion or partial-execution facts in the receipt; subsequent actions simply require a fresh `robot_observe` first. Replaying the same action identity returns the original persisted receipt, and an `unknown` execution state cannot be cleared merely by taking a fresh observation.

`ProgramRunner(harness.program_services())` receives a frozen `ProgramServices` bundle containing the `Store`, `program`-role validation/invocation/`effect` callbacks, observation ID and profile snapshots, and callbacks to query or cancel actions owned by that `program_id`. The runner holds no reference to `Harness`, `ToolRegistry`, `robot`, Harness locks, or raw cancellation events—the server-side `Harness` retains sole ownership of those states. Dynamic plugins are checked through the same registry for schema validity, role permissions, availability, and physical-action review requirements. Cancellation sets the active-action event only when its `program_id` matches the calling program, preventing one program from cancelling another's motion.

CPU validation entry points include `tests/test_robot_boundaries.py`, `test_robot.py`, `test_runtime_shutdown.py`, and `test_runtime_lifecycle.py`, alongside existing batch, dual-arm, gripper, speed, and contact-reference suites. Boundary tests run in a fresh Python interpreter that blocks importing `Harness`, the process owner, renderers, and PyTorch before loading the pure contracts and compilers; process tests use a lightweight JSONL fake worker to cover cancellation, broken pipes, OOM classification, and exit confirmation. Live Isaac trajectories and task outcomes must still be verified through independent simulation validation.

Once an idle GPU lease is acquired, run the model-free current interface validation matrix in a fresh directory:

```sh
python scripts/robot_validation.py --matrix current --gpu <leased-gpu> --run-dir <fresh-directory> --task stack_bowls
```

The script retains `--matrix legacy` as its default for backward compatibility. Under `--matrix current`, every action routes through `Harness`, using the measured end-effector pose for a default 5 mm lift-and-return to verify: single-arm preview without advancing the simulation clock, pausing at an observation checkpoint and resuming from the same cached plan, unequal-length dual-arm stage sequences with measured simultaneous motion, synchronized gripper command changes during arm motion, a three-step wait, and stop cancellation requested after live execution progress begins. `--displacement-m` accepts values in `(0, 0.02]` and `--jaw-goal` accepts values in `[0.5, 1.0]` (the jaw target must differ from the current command and is restored afterward). Action admission is closed after the stop test completes.

`validation-report.json` incrementally records requests, receipts, observation/trajectory references, source file hashes, and shutdown confirmations, while videos are saved as observer artifacts. The matrix cannot be marked as passing if worker process exit, reader thread exit, or native simulator shutdown lacks confirmation. Because the matrix runs with `execution_role=fixed_interface_validation_without_model` and `task_success=null`, its conclusions apply strictly to interface and execution evidence—never substituting for task success rate evaluation. `tests/test_robot_matrix.py` exercises the matrix logic itself on CPU using real compilation, `Harness`, and batch scheduling code paired with a synthetic planner/follower; those CPU tests do not replace live simulation validation.

The validation matrix also exercises a real isolated Python program: a fixed operator approves a cached plan and cancels a second run while paused for review, verifying that the native simulation clock does not advance. The missing-terminal-frame recovery check completes a real two-step wait, intentionally drops the returned terminal observation while keeping the `completed` receipt, verifies that the stale observation cannot admit a new action, and then restores admissibility via a fresh `robot_observe` (explicitly tagged as fault injection rather than a natural camera failure).
